## 2. Part A Findings

### A1. ID Format Analysis
- **Prisma Schema (`prisma/schema.prisma`)**:
  All 9 models use `@default(uuid())` for their primary keys (`id String @id @default(uuid())`). No model uses CUID.
- **Database Inspection**:
  Inspection across all 9 tables (78 total records) confirmed that 100% of IDs are valid UUIDv4 strings (e.g. `35a575ce-0109-4591-9f5e-97bb9b100442`). Zero non-UUID IDs exist in the database.
- **Validators Inspection**:
  - `src/lib/validators/matches.ts`, `messages.ts`, `reviews.ts`, `events.ts` validate IDs using `z.string().trim().min(1)`.
  - None of the active validator schemas strictly invoke `.cuid()`, so valid UUIDs are already accepted by the validators.
  - However, in prior documentation and changelogs (`PROJECT_STATUS.md`, `P2.2-P2.3-validation.md`), ID fields were described as CUIDs. All documentation and parameter descriptions must accurately specify UUID format.

### A2. Email Normalization Analysis
- **Registration (`src/app/api/auth/register/route.ts`)**:
  Lowercases and trims email: `const normalizedEmail = body.email.toLowerCase().trim();`.
- **Login (`src/lib/auth.ts`)**:
  Queries directly with unnormalized credentials: `prisma.user.findUnique({ where: { email: credentials.email } })`.
- **Database Email Casing**:
  Querying the database revealed that **0** out of 13 existing users have uppercase letters in their email. All existing stored emails are lowercase.
- **Discrepancy & Fix**:
  Because SQLite unique strings are case-sensitive by default, attempting to log in with `Alex@example.com` or `Rimi@gmail.com` fails in `src/lib/auth.ts`.
  Fix: Normalize credentials email in `src/lib/auth.ts` using `const normalizedEmail = credentials.email.toLowerCase().trim();`.

### A3. Verification Test Additions
- Extend `scripts/validation-check.mjs`:
  1. Test that harmless GET requests passing real UUID parameters (`GET /api/messages?matchId=<uuid>` and `GET /api/reviews?toUserId=<uuid>`) successfully pass Zod validation.
  2. Test that NextAuth sign-in succeeds identically with mixed-case email (`ALEX@EXAMPLE.COM` and `alex@example.com`).

## 4. Planned Schema Changes

### 1. Prisma Enums
Define explicit enums supported by Prisma 6.4 on SQLite:
```prisma
enum MatchStatus {
  PENDING
  ACCEPTED
  DECLINED
}

enum AttendanceStatus {
  GOING
  MAYBE
  CANCELLED
}

enum ProficiencyLevel {
  Beginner
  Intermediate
  Advanced
  Expert
}
```
Update model fields:
- `Match.status`: `MatchStatus @default(PENDING)`
- `EventAttendee.status`: `AttendanceStatus @default(GOING)`
- `UserSkillsTeach.proficiency`: `ProficiencyLevel`

### 2. Unique Constraints
- `Match`: Add `@@unique([userAId, userBId, matchedSkillId])` to prevent duplicate connection requests for the same skill.
- Keep existing unique constraints:
  - `UserSkillsTeach`: `@@unique([userId, skillId])`
  - `UserSkillsLearn`: `@@unique([userId, skillId])`
  - `EventAttendee`: `@@unique([eventId, userId])`

### 3. Query Indexes
Add indexes reflecting existing query and join patterns:
- `Match`: `@@index([userAId])`, `@@index([userBId])`, `@@index([matchedSkillId])`
- `Message`: `@@index([matchId, createdAt])`, `@@index([senderId])`
- `Event`: `@@index([dateTime])`, `@@index([hostId])`
- `EventAttendee`: `@@index([userId])`, `@@index([eventId])`
- `Review`: `@@index([toUserId])`, `@@index([fromUserId])`
- `UserSkillsTeach`: `@@index([skillId])`
- `UserSkillsLearn`: `@@index([skillId])`

### 4. Relation `onDelete` Rules Matrix
| Relation | Parent | Child Field | Current Rule | Planned Rule | Reason |
|---|---|---|---|---|---|
| User -> UserSkillsTeach | User | `userId` | `Cascade` | `Cascade` | User deletion removes taught skills |
| Skill -> UserSkillsTeach | Skill | `skillId` | `Cascade` | `Cascade` | Skill deletion cleans up teach mapping |
| User -> UserSkillsLearn | User | `userId` | `Cascade` | `Cascade` | User deletion removes learned skills |
| Skill -> UserSkillsLearn | Skill | `skillId` | `Cascade` | `Cascade` | Skill deletion cleans up learn mapping |
| User -> Match (userA) | User | `userAId` | `Cascade` | `Cascade` | User deletion cleans up user's matches |
| User -> Match (userB) | User | `userBId` | `Cascade` | `Cascade` | User deletion cleans up user's matches |
| Skill -> Match | Skill | `matchedSkillId` | `Cascade` | `Cascade` | Skill deletion removes matches for that skill |
| User -> Event (host) | User | `hostId` | `Cascade` | `Cascade` | User deletion cleans up hosted events |
| Event -> EventAttendee | Event | `eventId` | `Cascade` | `Cascade` | Event cancellation/deletion deletes attendees |
| User -> EventAttendee | User | `userId` | `Cascade` | `Cascade` | User deletion deletes attendance records |
| User -> Review (fromUser) | User | `fromUserId` | `Cascade` | `Cascade` | User deletion cleans up given reviews |
| User -> Review (toUser) | User | `toUserId` | `Cascade` | `Cascade` | User deletion cleans up received reviews |
| Match -> Message | Match | `matchId` | `Cascade` | `Cascade` | Match deletion cleans up message conversation |
| User -> Message (sender) | User | `senderId` | `Cascade` | `Cascade` | User deletion removes sent messages |

All 14 relation edges already specify `onDelete: Cascade`. This guarantees that deleting any user, event, skill, or match will not leave orphan rows or cause foreign key violations.
