# Plan: P2.1 — API Authentication & Authorization (Ownership) Hardening

## 1. Goal & Context
Secure every API endpoint in SkillSwap (`src/app/api/**`) against unauthorized access, privilege escalation, and cross-user data tampering. Ensure:
1. Unauthenticated requests to protected endpoints return `401 Unauthorized`.
2. Authenticated requests attempting to modify or access resources belonging to other users return `403 Forbidden` (or `404 Not Found` if the target entity does not exist).
3. The authenticated user ID is derived strictly from the server-side NextAuth session, never accepted from request bodies or URL parameters for ownership assignments.
4. No sensitive fields (such as `passwordHash`) are ever leaked in API responses.
5. Successful API response shapes remain 100% backward-compatible with existing frontend pages.

## 4. Reusable Helpers Specification (`src/lib/api-auth.ts`)

```typescript
import { getServerSession } from "next-auth";
import { NextResponse } from "next/server";
import { authOptions } from "@/lib/auth";
import { prisma } from "@/lib/prisma";
import type { Match } from "@prisma/client";

export type AuthResult =
  | { user: { id: string; email: string; name: string }; errorResponse: null }
  | { user: null; errorResponse: NextResponse };

export async function requireSession(): Promise<AuthResult> {
  const session = await getServerSession(authOptions);
  if (!session?.user?.email) {
    return {
      user: null,
      errorResponse: NextResponse.json({ error: "Unauthorized" }, { status: 401 }),
    };
  }

  const user = await prisma.user.findUnique({
    where: { email: session.user.email },
    select: { id: true, email: true, name: true },
  });

  if (!user) {
    return {
      user: null,
      errorResponse: NextResponse.json({ error: "User not found" }, { status: 404 }),
    };
  }

  return { user, errorResponse: null };
}

export type MatchParticipantResult =
  | { match: Match; isUserA: boolean; isUserB: boolean; errorResponse: null }
  | { match: null; isUserA: false; isUserB: false; errorResponse: NextResponse };

export async function getMatchForParticipant(
  matchId: string,
  userId: string
): Promise<MatchParticipantResult> {
  const match = await prisma.match.findUnique({
    where: { id: matchId },
  });

  if (!match) {
    return {
      match: null,
      isUserA: false,
      isUserB: false,
      errorResponse: NextResponse.json({ error: "Match not found" }, { status: 404 }),
    };
  }

  const isUserA = match.userAId === userId;
  const isUserB = match.userBId === userId;

  if (!isUserA && !isUserB) {
    return {
      match: null,
      isUserA: false,
      isUserB: false,
      errorResponse: NextResponse.json(
        { error: "Forbidden: You are not a participant in this match" },
        { status: 403 }
      ),
    };
  }

  return { match, isUserA, isUserB, errorResponse: null };
}
```

## 5. Security & Architecture Considerations
1. **Chat Messages Across States:**
   The prompt specifically notes:
   > "Only allow sending when the match status is ACCEPTED, but FIRST check how /api/conversations builds its list; if the app currently allows chatting in other statuses, do not break it, and report it to me instead."
   Analysis revealed that `/api/conversations` loads all matches regardless of status (`PENDING`, `ACCEPTED`, `DECLINED`), and `/chat` allows messaging across any active conversation. Enforcing `status === "ACCEPTED"` on `POST /api/messages` would break messaging on pending connection requests in the existing UI. Therefore, participant ownership is strictly verified (403 if not participant), but we do not unilaterally block non-ACCEPTED states, and we clearly report this finding.
2. **Acceptance Permission Model:**
   In `POST /api/matches`, `userAId` is always the initiator (sender) and `userBId` is the target (recipient). Hence, only `userBId` has the legitimate authority to change status to `ACCEPTED` or `DECLINED`. If `userAId` attempts to accept their own request, `PATCH /api/matches/[id]` rejects with `403 Forbidden`.
3. **Password Hash Elimination:**
   `src/app/api/user/profile/route.ts` was leaking `passwordHash` in both `GET` and `PUT` responses. Switching to an explicit field selection or sanitized return guarantees `passwordHash` is never sent over the wire.
4. **Database Safety:**
   Backup of `prisma/dev.db` was created at `D:\dev.db.backup` prior to running any verification scripts.
   The verification script `scripts/security-check.mjs` tests denial cases only (401 and 403 responses), leaving zero database modifications or orphan test records behind.
