# P2.6 Plan — Safe, Backward-Compatible Pagination and Result Limits

## 1. Objectives & Scope
Add safe, backward-compatible pagination and result limits to all 5 list endpoints:
- `GET /api/matches`
- `GET /api/events`
- `GET /api/conversations`
- `GET /api/messages`
- `GET /api/reviews`

### Strict Rules:
1. **100% Backward Compatible**: With NO query parameters passed, every endpoint returns the exact same data and response shape as today. Frontend pages (`dashboard`, `events`, `chat`, `reviews`) will work with zero code modifications.
2. **Response Shapes**: All 5 existing endpoints return objects (`{ matches, currentUser }`, `{ events }`, `{ conversations }`, `{ messages }`, `{ reviews, avgRating, totalReviews }`). We will preserve all existing fields and add a new `pagination` field to the object response, plus standard pagination HTTP response headers (`X-Total-Count`, `X-Page` / `X-Next-Cursor`, etc.).
3. **No UI Changes**: No "Load more" or infinite scroll UI will be built in this task (deferred to Phase 3/4).
4. **Ordering & Matching Guarantees**:
   - `matches`: Mutual match computation and tab counts require full candidate scoring. Pure `computeAllMatches` in `src/lib/matching.ts` remains intact, all 19 unit tests pass. Pagination is applied to the sorted results without altering the ranking or mutual flags.
   - `events`: Ordered by `dateTime: "asc"`, tie-breaker `id: "asc"`.
   - `conversations`: Ordered by `createdAt: "desc"`, tie-breaker `id: "asc"`.
   - `messages`: Default returns the latest 200 messages in chronological `asc` order. With `cursor`, returns older messages before cursor in chronological `asc` order. Polling in `chat/page.tsx` continues to see the latest messages.
   - `reviews`: Ordered by `createdAt: "desc"`, tie-breaker `id: "desc"`. `avgRating` and `totalReviews` reflect total profile stats.
5. **No DB Schema Changes**: No schema modifications, no migrations, no seed resets.

## 2. Per-Endpoint Behavior & Chosen Default Caps

| Endpoint | Current Response Shape | Ordering | Default Cap (No Params) | Client Limit Allowed | Pagination Type & Params | Metadata Location |
|---|---|---|---|---|---|---|
| `GET /api/matches` | Object: `{ currentUser, matches }` | `matchScore desc, sharedInterests desc, name asc` | 100 | 1..100 | Page-based (`page`, `limit`) | `pagination` object + `X-*` headers |
| `GET /api/events` | Object: `{ events }` | `dateTime asc, id asc` | 100 | 1..100 | Page-based (`page`, `limit`) | `pagination` object + `X-*` headers |
| `GET /api/conversations` | Object: `{ conversations }` | `createdAt desc, id asc` | 100 | 1..100 | Page-based (`page`, `limit`) | `pagination` object + `X-*` headers |
| `GET /api/messages` | Object: `{ messages }` | Latest messages `asc` (from `createdAt asc, id asc`) | 200 | 1..100 | Cursor-based (`cursor`, `limit`) | `pagination` object + `X-*` headers |
| `GET /api/reviews` | Object: `{ avgRating, totalReviews, reviews }` | `createdAt desc, id desc` | 50 | 1..100 | Page-based (`toUserId`, `page`, `limit`) | `pagination` object + `X-*` headers |

### Justification of Caps:
- **Matches (100)**: Current active user set is 12 candidates. 100 is high enough to return all candidates today with zero truncation, while protecting server memory against unbounded growth.
- **Events (100)**: Current database has 3 sample events. 100 encompasses all upcoming community meetups.
- **Conversations (100)**: Active users have 1-2 active matches. 100 protects the chat sidebar while returning all active swaps.
- **Messages (200)**: Chats in local demo have 1-5 messages. Returning latest 200 ensures chat stream displays full recent context immediately on load without extra round-trips.
- **Reviews (50)**: Current peers have 0-2 reviews. 50 covers full peer review histories cleanly.

## 3. Query Parameter Design & Zod Schemas

### A. Page Pagination Query Schema (`src/lib/validators/pagination.ts`):
```ts
export const pagePaginationQuerySchema = z.object({
  page: z
    .string()
    .optional()
    .transform((val) => (val ? parseInt(val, 10) : undefined))
    .pipe(z.number().int().min(1).optional()),
  limit: z
    .string()
    .optional()
    .transform((val) => (val ? parseInt(val, 10) : undefined))
    .pipe(z.number().int().min(1).max(100).optional()),
});
```

export const getReviewsQuerySchema = z.object({
  toUserId: z.string().uuid("Invalid user ID"),
  page: z
    .string()
    .optional()
    .transform((val) => (val ? parseInt(val, 10) : undefined))
    .pipe(z.number().int().min(1).optional()),
  limit: z

### D. Validation Error Responses:
Invalid parameters (`limit=0`, `limit=abc`, `limit=100000`, `page=0`, `cursor=invalid-uuid`) will be rejected by `parseQuery` and return the standard HTTP 400 JSON:
`{ "error": "Invalid query parameters", "details": [...] }`.
Session checks run BEFORE query validation, preserving existing security contracts.

## 4. Metadata Contract & Headers

### Page-based:
- Object field `pagination`:
  ```json
  {
    "total": 12,
    "page": 1,
    "limit": 100,
    "totalPages": 1,
    "hasNextPage": false,
    "hasPrevPage": false
  }
  ```
- HTTP Response Headers:
  - `X-Total-Count`: `12`
  - `X-Page`: `1`
  - `X-Limit`: `100`
  - `X-Total-Pages`: `1`
  - `X-Has-Next-Page`: `false`
  - `X-Next-Page`: `2` (omitted if `hasNextPage` is false)

### Cursor-based (Messages):
- Object field `pagination`:
  ```json
  {
    "total": 1,
    "limit": 200,
    "hasMore": false,
    "nextCursor": null
  }
  ```
- HTTP Response Headers:
  - `X-Total-Count`: `1`
  - `X-Limit`: `200`
  - `X-Has-More`: `false`
  - `X-Next-Cursor`: `<message-id>` (omitted if `hasMore` is false)
