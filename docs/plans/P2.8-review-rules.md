# P2.8 Plan — Review Rules & Duplicate Prevention

## 1. Objectives & Scope
Enforce strict review submission business logic in `POST /api/reviews` (the final task of Phase 2):
1. Exactly one review allowed per reviewer and reviewed person (`fromUserId` + `toUserId`).
2. Reviews are strictly permitted only after an `ACCEPTED` match exists between the reviewer and recipient.
3. Attempting to review the same person again returns HTTP 409 Conflict with `{ "error": "You have already reviewed this person." }`.
4. Race-safety: Two concurrent review submissions must not both succeed.
5. All checks are rejection-only: zero database rows created in verification.

## 3. Data Model Analysis (`Review`)
Current `Review` schema in `prisma/schema.prisma`:
```prisma
model Review {
  id         String   @id @default(uuid())
  fromUserId String
  toUserId   String
  rating     Int      // 1 to 5 stars
  comment    String
  createdAt  DateTime @default(now())

  fromUser   User     @relation("ReviewsGiven", fields: [fromUserId], references: [id], onDelete: Cascade)
  toUser     User     @relation("ReviewsReceived", fields: [toUserId], references: [id], onDelete: Cascade)

  @@index([toUserId])
  @@index([fromUserId])
}
```
- The `Review` model tracks `fromUserId` and `toUserId`. It has **no** `matchId` column, and per task instructions, none will be added.
- The rule is strictly scoped to `(fromUserId, toUserId)` pairs.

## 5. Chosen Enforcement Strategy
1. **Database-Level Constraint**:
   - Because 0 duplicates exist, add `@@unique([fromUserId, toUserId])` to the `Review` model in `prisma/schema.prisma`.
   - Test applying via plain `npx prisma db push` (strictly without `--accept-data-loss` or `--force-reset`).
   - If Prisma applies the unique index cleanly without prompting for data loss, retain `@@unique([fromUserId, toUserId])`.
   - If Prisma asks for table recreation / data loss, skip the schema constraint, retain `@@index([fromUserId, toUserId])`, and rely on transactional application-level locking.
2. **Application-Level Enforcement in `POST /api/reviews`**:
   - Execution order:
     1. Session check (`requireSession`) -> 401 Unauthorized
     2. Rate limit check (`rateLimit("reviews:create:userId")`) -> 429 Too Many Requests
     3. Request body validation (`parseBody(req, createReviewSchema)`) -> 400 Bad Request
     4. Self-review check (`auth.user.id === toUserId`) -> 400 Bad Request (`"You cannot review yourself"`)
     5. Target user existence check -> 404 Not Found (`"Recipient user not found"`)
     6. **Duplicate review check**: Query existing review where `fromUserId = auth.user.id` and `toUserId = toUserId`. If found, return HTTP 409 Conflict with `{ "error": "You have already reviewed this person." }`.
     7. **Accepted match check**: Query match where `(userAId = auth.user.id AND userBId = toUserId) OR (userAId = toUserId AND userBId = auth.user.id)` and `status = "ACCEPTED"`. If no match exists or status is not `ACCEPTED`, return HTTP 403 Forbidden with `{ "error": "You can only review users you have an accepted match with" }`.
     8. **Create review with race-condition catch**: Wrap insert in `try/catch`. If a concurrent request creates a review simultaneously and triggers Prisma error `P2002` (Unique constraint failed), catch it and return HTTP 409 Conflict with `{ "error": "You have already reviewed this person." }`.

## 7. Risks & Mitigations
- **SQLite Schema Migration Risk**: Adding `@@unique` on SQLite could potentially prompt for table recreation. We will test plain `prisma db push` and abort immediately if any data loss prompt appears.
- **Order of Checks**: In the seeded database, Alex Kumar already reviewed Priya Patel, but their seeded match is `PENDING`. By running the duplicate check (409) before the match status check (403), Alex attempting to re-review Priya cleanly returns 409 without needing an ACCEPTED match or modifying seed data.
- **Zero Data Creation**: All check scripts use rejection cases (self-review 400, unaccepted match 403, duplicate review 409). No database rows are inserted.
