# P2.7 Plan — Rate Limiting on Login, Registration, and Write Endpoints

## 1. Objectives & Scope
Implement an in-memory, zero-dependency rate limiter with injectable clock to safeguard authentication (login, registration) and write operations (`POST`, `PATCH`, `PUT`) against spam, brute force, and abuse, while strictly ensuring normal user interactions are never impeded.

### Strict Rules:
1. **Normal Use Unblocked**: Generous thresholds tailored to human usage, restrictive strictly against automation and abuse.
2. **Backward-Compatible Responses**: Successful endpoints retain exact response shapes. Rate-limited requests return HTTP 429 with `{ "error": "Too many requests. Please try again in N seconds." }`, `Retry-After` header, and `X-RateLimit-Limit` / `X-RateLimit-Remaining` headers.
3. **No UI Changes**: Frontend retains its current behavior. If the frontend displays 429 errors (e.g. auth page or fetch toasts), document exactly what the user sees.
4. **No Database Writes in Checks**: Validation and security checks in this task must create zero database records.
5. **No Schema Changes / Zero New Dependencies**: Pure TypeScript implementation using standard Web Fetch & Next.js APIs.
6. **Execution Order**: Session check first (401), rate limit check second (429), input validation third (400), business logic last. Rate-limited requests must never query or mutate the database.

## 2. Limiter Architecture & Design (`src/lib/rate-limit.ts`)

### A. Storage & Hot-Reload Resilience
- **Storage Interface**:
  ```ts
  export interface RateLimitStore {
    get(key: string): { count: number; expiresAt: number } | undefined;
    increment(key: string, windowMs: number): { count: number; expiresAt: number };
    cleanup(now: number): void;
    reset(): void;
  }
  ```
  This abstraction allows seamless drop-in replacement with Redis or Upstash in task P7.1 without modifying route handlers.
- **`globalThis` Persistence**:
  In Next.js development mode, hot-module replacement (HMR) re-evaluates module scopes. By anchoring the store to `globalThis.__rateLimitStore`, counters persist across fast refreshes.
- **Memory Leak Protection**:
  On every rate-limit check or window rollover, expired keys (`expiresAt <= now`) are pruned, preventing unbounded memory growth.

### B. Injectable Clock & Testing
- The limiter accepts an optional `clock?: () => number` parameter (defaulting to `Date.now`).
- Unit tests can fast-forward fake time deterministically to verify window expiration, counter resets, and `Retry-After` math without real-time sleep delays.

### C. Testing Switch (`RATE_LIMIT_DISABLED`)
- Environment variable `RATE_LIMIT_DISABLED=true` bypasses rate limiting.
- **Production Guard**: `process.env.NODE_ENV !== "production" && process.env.RATE_LIMIT_DISABLED === "true"`. In production, this flag is strictly ignored.
- Documented in `.env.example`.

## 3. Rate Limit Keys & Route Policies

### Key Derivation Strategy:
- **Authenticated Requests**: `<action>:<userId>` (e.g. `messages:create:0fa9d2b2-3022-4467-88f5-44fb6b4f7623`). Prevents single-user flooding without impacting other users sharing a corporate NAT/IP.
- **Anonymous Requests (Registration)**: `register:<ip>` where `<ip>` is extracted from the first entry of the `x-forwarded-for` header (with fallback to `127.0.0.1`).
- **Credentials Login**:
  - `login:ip_email:<ip>:<normalizedEmail>`: 10 attempts per 15 minutes. Prevents credential stuffing against a specific account without locking out entire corporate networks.
  - `login:ip:<ip>`: 50 attempts per 15 minutes. Blocks high-volume distributed password guessing from an offending IP.

### Limits Table & Reasoning:

| Route / Action | Method | Key | Limit | Window | Reasoning |
|---|---|---|---|---|---|
| Login (Authorize) | - | `login:ip_email:<ip>:<email>` | 10 | 15 min (900s) | Allows human typos while mitigating targeted brute force |
| Login (Authorize) | - | `login:ip:<ip>` | 50 | 15 min (900s) | Stops IP-wide dictionary and credential stuffing attacks |
| `/api/auth/register` | `POST` | `register:<ip>` | 5 | 1 hour (3600s) | Generous for legitimate account signups, halts spam account creation |
| `/api/messages` | `POST` | `messages:create:<userId>` | 30 | 1 min (60s) | Generous 1 message every 2s for rapid human chatting; halts bots |
| `/api/matches` (Connect) | `POST` | `matches:create:<userId>` | 20 | 1 hour (3600s) | Human connection requests; prevents mass spamming all members |
| `/api/matches/[id]` (Accept/Decline) | `PATCH` | `matches:update:<userId>` | 60 | 1 hour (3600s) | Ample for triaging inbox connection invitations |
| `/api/reviews` | `POST` | `reviews:create:<userId>` | 10 | 1 hour (3600s) | Real reviews take minutes to write; blocks fake review floods |
| `/api/events` | `POST` | `events:create:<userId>` | 10 | 1 hour (3600s) | Host meetup creation; prevents spam event creation |
| `/api/events/[id]/rsvp` | `POST` | `events:rsvp:<userId>` | 60 | 1 hour (3600s) | Ample for browsing and RSVPing across local meetups |
| `/api/skills` | `POST` | `skills:create:<userId>` | 20 | 1 hour (3600s) | Ample for adding custom community skills |
| `/api/user/profile` | `PUT` | `profile:update:<userId>` | 30 | 1 hour (3600s) | Ample for adjusting bio, location, and teaching/learning skills |
| GET Endpoints | `GET` | *Unthrottled* | - | - | Chat polling every 3s and page loads remain completely unthrottled |

## 4. Login Handling in NextAuth (`src/lib/auth.ts`)
- In NextAuth `authorize(credentials, req)`, rate limits are evaluated before any database lookup.
- If rate limited:
  ```ts
  throw new Error(`Too many login attempts. Please try again in ${rl.retryAfterSeconds} seconds.`);
  ```
- **Security Guarantee**: Fails without looking up user existence, preventing user enumeration or timing leaks.
- **Frontend Presentation**: `src/app/auth/page.tsx` catches `result.error` from `signIn("credentials", ...)` and renders it into the alert box:
  `Too many login attempts. Please try again in N seconds.`

## 5. Execution Order Inside Routes
```
Incoming Request
  │
  ▼
1. requireSession() ──────────────► 401 Unauthorized (if unauthenticated on protected routes)
  │
  ▼
2. rateLimit(key, options) ───────► 429 Too Many Requests (with Retry-After header)
  │
  ▼
3. parseBody() / parseQuery() ────► 400 Bad Request (with standard validation details)
  │
  ▼
4. Database & Business Logic ─────► 200 OK / 201 Created
```

## 6. Risks & Limitations
1. **In-Memory Volatility**: Counters reset whenever the Node.js server process restarts. Acceptable for dev/single-instance, replaced by Redis/Upstash in P7.1.
2. **Multi-Instance / Serverless Inefficacy**: In-memory state is not shared across horizontal worker processes. Handled during cloud deployment in Phase 7.
3. **`x-forwarded-for` Trust**: The first IP in `x-forwarded-for` is trusted. In production (P6.1), reverse proxies (Vercel, Cloudflare) must be configured to overwrite or sanitize this header.
